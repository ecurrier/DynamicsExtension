# Popup harness

Runs the built popup in a normal browser tab with the Chrome extension APIs replaced by an in-memory shim that answers every page command with sample Dataverse data. Useful for checking layout and flows without loading the extension or opening a Dynamics org.

```bash
npm run build
npm run harness
npx serve -l 5173 .output/chrome-mv3
```

Then open `http://localhost:5173/harness.html` (popup), `http://localhost:5173/harness-results.html` (results viewer), or `http://localhost:5173/harness-traces.html` (plugin trace viewer, seeded with a fake launch from tab 1).

`chrome-shim.js` seeds storage directly at the current schema version (environments, a service principal, a form preset, and a user code Template starred as the table default), so the migrations are covered by unit tests rather than by the harness.

Site access starts out ungranted so the "Allow access" banners render; add `?granted=1` to pre-grant it, and open `harness?mode=window&tabId=1` (without `.html`, because `serve` drops the query string when it redirects to the clean URL) to see the popup as a pinned window. `harness-sidepanel` is the same app as the side panel; it reads its mode from the path, so it needs no query string, and the browser viewport has to be narrowed to panel width to see the layout it gets in Chrome. Adding `?closedTab=1,3` there leaves no Dynamics tab open, which is how the "No Dynamics tab connected" state renders.

In the pinned-window harness the Data Transporter, Trace Viewer, and Open in viewer buttons become split buttons: the primary action fills the harness window with the Workspace and the menu still opens it in a new tab. `chrome.windows.getCurrent` reports the browser tab as a normal-state window, so the grow-to-fit call logs through `windows.update` without resizing anything.

The Code Generation module is backed by `codegen.getTableModel` (a sample table with a money column, a DateOnly date, a multi-select choice, a two-target owner lookup, a helper column, a bookkeeping column, and the extra columns listed under Record Columns below, so the type map and system-column toggle are visible) and `codegen.getGlobalChoices`. The seeded user Template "Contoso model" wraps the built-in C# class in a namespace so Generate Table Class shows a customised default.

The Plug-ins module's Packages area is backed by three package fixtures: "Contoso.Plugins" (managed, with an Active layer on top of its solution), "Fabrikam.Integration" (managed, no unmanaged layer), and "Contoso.Workflows" (unmanaged). The `pluginPackages.*` command stubs answer the page connection and the fake `fetch` serves `pluginpackages`, `plugintypes`, and `msdyn_componentlayers` for the environment connection. A `PATCH pluginpackages(...)` logs the upload length and bumps the package's modified time without touching its version, mirroring what the real API is documented to do; the "Update again from" button needs a real file picked through the browser, so it is exercised manually.

The Admin Area's Dirty Columns card is backed by `utilities.getDirtyColumns`, which returns four sample changes on the account form: a renamed Account Name, a hidden Main Phone, a read-only Onboarding Status whose submit mode is `never`, and a Credit Limit with no control on the form. Selecting a row goes through the `utilities.revealFormColumn` stub, which only logs; the real scroll and flash need an org.

The Web API module's Record Columns Area reads the same `codegen.getTableModel` table, which also carries a phone, a memo, a single-target and a two-target Customer lookup, a Boolean, a whole number, a calculated column that is not valid for update, a user-local and a time-zone independent date and time, `modifiedon`, a non-primary Uniqueidentifier, an image, a file, and forty filler text columns so the list is long enough to scroll and filter. `webapi.getRecordValues` answers from a mutable record in the shim, with formatted values and lookup annotations; `utilities.getFormAttributes` puts only four of its columns on the form, which is what the Not on form filter narrows to. `webapi.saveRecord` applies the payload to that record, including lookups bound or cleared through `@odata.bind`, and logs `[harness] webapi.saveRecord` with the body; a name of `FAIL` throws a plug-in style error instead, so the save bar's error path renders. `webapi.getFormState` reports the form clean unless the harness URL has `?dirty=1`, which is how the "form has unsaved changes" prompt after a save is reached, and `webapi.refreshForm` only logs. `__harness.setRecordValues({ ... })` changes the record as a save on the form would, and firing a window `focus` event afterwards reloads the values the way returning to the Area does; `__harness.navigate()` then moves to another record, which drops the remaining Drafts with a notice.

The bound-tab watcher is driven from the console through `window.__harness`. `__harness.navigate()` changes the record `utilities.getPageTarget` reports and fires `webNavigation.onHistoryStateUpdated`, which is how a model-driven app moves between records without a page load; passing the same record id back proves the watcher reads the target but skips the invalidation. `__harness.openView()` does the same for a view. `__harness.reload()` fires `tabs.onUpdated` with `status: "complete"`, which always invalidates because a real load wipes the Page Bridge. `__harness.closeTab(1)` fires `tabs.onRemoved` so the "Power Tools lost its tab" banner renders; `tabs.query` then offers tab 3 ("Active Accounts"), and picking it rebinds the session and moves the watcher onto that tab. `__harness.reopenTab(1)` puts it back. `__harness.activateTab(3)` fires `tabs.onActivated` for a Dynamics tab, which the side panel follows, and `__harness.activateOtherSite()` fires it for tab 9 (`make.powerapps.com`), which the panel ignores so the binding survives a trip to another site. Each control takes the tab id as its last argument, so an event aimed at a tab the session is not bound to can be checked to do nothing.

The Extension settings section carries an "Open In Side Panel" toggle. Flipping it in the harness only writes the setting: `setPanelBehavior` is called from the background service worker, which the harness does not run, so the shim records the call but nothing changes what the toolbar icon does. The "Open in the side panel" toolbar button does work end to end here, logging `sidePanel.open` with the bound tab id.

The Security Module is backed by eight role fixtures that deliberately include business unit copies: "Basic User" exists in three business units and "Sales Manager" in two, both pointing at a root role, plus a "Field Technician" that exists only in a child business unit with no root. That is what makes the deduped role lists show "3 copies" and "2 copies" and proves a child-only role is not dropped. `security.getRolePrivileges` generates the eight table privileges across Account, Contact, Incident and Opportunity at mixed depths, with System Administrator pinned at Organization; `security.addPrivilegesRole` throws for that role, so a privilege depth run against it produces a partial failure with a real message. `security.searchSystemUsers` returns twelve users so Select all and a multi-page bulk run are reachable.

`harness-security` is the Security Tools Workspace. It reads its launch payload from seeded session storage, so it opens straight onto Role Compare; add `?securityTool=privileges` to open on the Privilege Editor instead. Removing the seed is what produces the "No security tools session" state.

The Impersonation Area's role list is backed by `security.getSystemUserRoles`: Jane Doe holds three roles directly and one through the Field Sales team, Contoso User 3 holds roles only through teams, and everyone else holds none, so the empty state renders for them. `impersonation.start` stores the roles the popup passes it, and the active view shows those instead of querying again.

The Records Area is backed by `utilities.generateFetchXml`, which on the sample form offers the current record query and one subgrid, and by `webapi.executeFetchXml`, which returns 120 sample accounts — below the 250-row cap, so the load-more path needs a larger fixture to exercise. `utilities.navigateToRecord` updates the mutable page target in the shim and logs, which is what makes the position caption and the row highlight move; in a real org the same refresh also arrives through `webNavigation.onHistoryStateUpdated`.

`harness-schema` is the Schema Tools Workspace, opening on Cross-Table Columns; add `?schemaTool=polymorphic` for the other tab. `schema.findAttributeAcrossTables` answers any name beginning `new_` with four tables: Account and Contact unmanaged, Case managed but editable, and Lead both a different type (Memo, which the tool flags) and locked by its managed solution. `schema.updateAttribute` throws for Contact, so a run across all four reads "2 of 3 applied, 1 failure" with the locked Lead never planned, and `schema.publishTables` then logs only the tables that succeeded. The polymorphic tool has no fixtures: it creates against a request shape that is not yet confirmed, so stubbing it would only prove the stub agrees with itself.

`harness-query-builder` is the Query Builder Workspace. It reads its launch payload from seeded session storage, so it opens from tab 1 on the page Connection with an empty editor, which shows the starting points (Blank, Paste Fetch XML, From a view, From the open page) beside the Fetch XML pane. Add `?queryConnection=environment` to open on the Contoso Dev Environment instead. Add `?queryFetchXml=` to open with a Query in the editor: `account` is a five-Column account Query; `tree` is an interleaved account Query that exercises the tree (nested `AND`/`OR` filters, an `in` condition with `<value>` children, two `order` rows, a `link-entity` to `contact`, a free-text comment, an Excluded `revenue` attribute, an unknown `custom-hint` element, and an `attribute` after the `filter` so Tidy has work to do); `nested` is an account Query with `top="25"`, an `OR` filter inside an `AND` filter and a many-to-one `link-entity` to `contact`, for the Web API tab; and `batch` is the long Query described below. The two parameters combine, for example `?queryFetchXml=batch&queryConnection=environment`. Removing the seed is what produces the "No Query Builder session" state.

Over the page Connection the `query.*` command stubs answer; over the Environment connection the Service Principal sends the real Web API requests and the fake `fetch` answers them. Both serve the same fixtures. The Table list is Account, Contact and User, but only Account and Contact have Columns. The account Table has a Choice, Status and Status Reason, a Boolean, a money and a whole number Column, a Memo, a user-local and a date-only date, a multi-select Choice, the Primary Contact and Parent Account lookups, an Owner, a helper Column with `attributeOf`, a Column that is not valid for read, and forty-eight filler Columns (`new_f001` to `new_f048`, display names such as "Loyalty Points" and "Credit Limit 2") so the 50-option cap of the pickers is reached and a display-name search can be tried while logical names lead. The contact Table has a two-target Customer lookup, a Choice, a date-only birthday, a Boolean and an Owner. Their relationships cover all three kinds: many-to-one to each other, to themselves and to User, one-to-many back from each lookup, and one many-to-many between them. The fake `fetch` answers the base Column request only when its `$select` holds base properties: a `$select` naming `MaxLength`, `Precision`, `Format`, `DateTimeBehavior`, `Targets` or `OptionSet` fails with a 400, as the real API does, and those properties come from the typed casts (`/Attributes/Microsoft.Dynamics.CRM.StringAttributeMetadata` and the others).

A Query Run on `account` pages through 130 accounts and one on `contact` through 12 contacts. The Workspace asks for 50 Records a page, so a first Query Run on `account` shows 50 Records and "more on the server". Each page that has more carries `morerecords` and a paging cookie whose `pagingcookie` attribute is URL-encoded twice; a request for a later page whose cookie does not come from the page before it fails with a `harness:` error. The fiftieth account is named `Fourth Coffee & Tea <Ltd> "East"`, so the cookie for page 2 holds `&`, `<` and `"`. `top` returns that many Records as one page, `aggregate="true"` returns one row with every alias set to the Record count, and `returntotalrecordcount="true"` adds the total count annotations. The stubs ignore filters, apart from an `in` condition on the primary key, which keeps only the listed Records. A `link-entity` to `contact` adds the account's primary contact Columns to its row under `alias.column` (or `contact1.column` without an alias), with their formatted-value and lookup annotations, lookups included under the same `alias.column` form; only the first `link-entity` is read, and the accounts without a primary contact (every third one) get no linked keys. A Query naming an attribute that no fixture Table has fails with the platform-style "doesn't contain attribute" error, and a Query Run on any other entity set fails with a 404. A Record lookup on a condition searches through `runQuery` with `top="25"`, so it lists the first 25 accounts or the 12 contacts whatever is typed.

`?queryFetchXml=batch` opens an account Query whose `accountid` `in` condition lists 600 GUIDs, 20 of which are fixture accounts, so the Query Run returns those 20. Its URL is longer than 30,000 characters, so over the Environment connection `runQuery` sends it as a `POST $batch`. The fake `fetch` reads the one `GET` line from the multipart body, which must hold an absolute `/api/data/v9.2/` URL, logs `[harness] $batch` with its length, and answers with `Content-Type: multipart/mixed; boundary=batchresponse_<id>` and one `application/http` part (`HTTP/1.1 200 OK`, a JSON content type, a blank line, the usual JSON result). For a failed Query Run it answers with a 400 envelope whose part is `HTTP/1.1 400 Bad Request` with `{"error":{"message":...}}`, so adding an unknown attribute to the batch Query shows the error path.

"From a view" lists four System Views of `account` (Public, a second Public, Quick Find with `{0}` placeholders, and Lookup) and, over the page Connection, two Personal Views. Over the Environment connection the fake `fetch` answers `savedqueries` with the same System Views and `userqueries` with a 403 privilege error, which is how the "Personal Views could not be read" note is reached. Other Tables have no views. "From the open page" lists the four `utilities.generateFetchXml` stubs; the first names `telephone1`, which the account fixture does not have, so the missing-Column warning shows when it is converted. The Developer Area's "Generate Query" dialog (search the navigation drawer for `fetch`) offers the `nested` Query as "Active Accounts in Accounting or named Contoso", so the URL in the dialog's Web API query tab can be compared with the Workspace's Web API tab; the dialog reads its Table metadata through the same `query.getTable` stub, on the page Connection. Its "Open in Query Builder" opens `harness-query-builder` in place of `query-builder.html` from the popup, handing the launch over through `sessionStorage` key `harness:queryBuilderLaunch`, which is read once, and opens the Workspace in place in `harness?mode=window&tabId=1&granted=1`.

The remembered Queries survive a reload of the same tab: the shim copies `local:workingQuery`, `local:queryHistory` and `local:storedQueries` into `sessionStorage` (keys `harness:local:<name>`) on every write and reads them back over the seed on load, so "edit, reload, restored" and the History and My queries panel can be checked. Run `sessionStorage.clear()` in the console and reload to start empty again. A working Query is restored only when the launch has no Fetch XML, so check it on `harness-query-builder` without `?queryFetchXml`.

The harness cannot show what a real org returns, and `.scratch/query-builder/smoke-test-phase-1.md` lists those checks. The fake responses follow the code's reading of Microsoft's documentation, so the paging cookie, the keys linked Columns arrive under, the `$batch` envelope, the views requests and the typed Column casts agree with the code, not necessarily with a server. Over the page Connection each stub replaces the whole page handler and receives the Fetch XML itself, so the page-side paging, `$batch` and metadata requests are not exercised at all. The Copy button's clipboard write cannot be checked in the browser pane, which refuses clipboard access.

The usability pass added fixtures for the reworked screens. `security.listSystemUsers` returns forty-two users whose names repeat across a small set of first and last names, which is what makes the Bulk Users filter worth using and lets the assemble-a-set-over-several-filters behaviour be exercised. `schema.findAttributeAcrossTables` answers any `new_` name with four tables spanning two attribute types, so the type-dependent property controls show and hide as the selection changes. Their current values come from `schema.readAttributeDetails`, read only for the selected columns: a maximum length of 100, or 2000 for a Memo. The real search asks only for properties every column type has, because type-specific ones such as `MaxLength` make the whole request fail. The Record Set Navigator view fixture names five attributes including a lookup and a link-entity attribute, so column derivation, formatted values and the link-entity exclusion are all visible. `schema.listPolymorphicLookups` returns two lookups on `account`: Related To with two targets, and Regarding with eighteen, which is long enough to scroll and to show the target filter. The create, add and remove stubs log rather than write, so a created lookup or an added target never appears in the list.

The navigation drawer opens with its search box focused; Ctrl+K opens the drawer from anywhere and focuses the box when the drawer is already open. Local storage seeds `recentAreas`, so while the harness sits on Admin the Recent section lists Cross-Table Columns, Record Access, and Developer. Searching for a Utility, for example `fetch`, opens its Area and outlines the card for a couple of seconds.
