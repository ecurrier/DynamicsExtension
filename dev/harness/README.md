# Popup harness

Runs the built popup in a normal browser tab with the Chrome extension APIs replaced by an in-memory shim that answers every page command with sample Dataverse data. Useful for checking layout and flows without loading the extension or opening a Dynamics org.

```bash
npm run build
npm run harness
npx serve -l 5173 .output/chrome-mv3
```

Then open `http://localhost:5173/harness.html` (popup), `http://localhost:5173/harness-results.html` (results viewer), or `http://localhost:5173/harness-traces.html` (plugin trace viewer, seeded with a fake launch from tab 1).

`chrome-shim.js` seeds storage directly at the current schema version (environments, a service principal, a form preset, and a user code Template starred as the table default), so the migrations are covered by unit tests rather than by the harness.

Site access starts out ungranted so the "Allow access" banners render; add `?granted=1` to pre-grant it, and open `harness?mode=window&tabId=1` (without `.html`, because `serve` drops the query string when it redirects to the clean URL) to see the popup as a pinned window. `harness-sidepanel` is the same app as the side panel; it reads its mode from the path, so it needs no query string, and the browser viewport has to be narrowed to panel width to see the layout it gets in Chrome. Adding `?closedTab=1,3` there leaves no Dynamics tab open, which is how the "No Dynamics tab connected" state renders.

In the pinned-window harness the Data Transporter, Trace Viewer, and Open in viewer buttons become split buttons: the primary action fills the harness window with the Workspace and the menu still opens it in a new tab. `chrome.windows.getCurrent` reports the browser tab as a normal-state window, so the grow-to-fit call logs through `windows.update` without resizing anything.

The Code Generation module is backed by `codegen.getTableModel` (a sample table with a money column, a DateOnly date, a multi-select choice, a two-target owner lookup, a helper column, and a bookkeeping column, so the type map and system-column toggle are visible) and `codegen.getGlobalChoices`. The seeded user Template "Contoso model" wraps the built-in C# class in a namespace so Generate Table Class shows a customised default.

The Plug-ins module's Packages area is backed by three package fixtures: "Contoso.Plugins" (managed, with an Active layer on top of its solution), "Fabrikam.Integration" (managed, no unmanaged layer), and "Contoso.Workflows" (unmanaged). The `pluginPackages.*` command stubs answer the page connection and the fake `fetch` serves `pluginpackages`, `plugintypes`, and `msdyn_componentlayers` for the environment connection. A `PATCH pluginpackages(...)` logs the upload length and bumps the package's modified time without touching its version, mirroring what the real API is documented to do; the "Update again from" button needs a real file picked through the browser, so it is exercised manually.

The Admin Area's Dirty Columns card is backed by `utilities.getDirtyColumns`, which returns four sample changes on the account form: a renamed Account Name, a hidden Main Phone, a read-only Onboarding Status whose submit mode is `never`, and a Credit Limit with no control on the form. Selecting a row goes through the `utilities.revealFormColumn` stub, which only logs; the real scroll and flash need an org.

The bound-tab watcher is driven from the console through `window.__harness`. `__harness.navigate()` changes the record `utilities.getPageTarget` reports and fires `webNavigation.onHistoryStateUpdated`, which is how a model-driven app moves between records without a page load; passing the same record id back proves the watcher reads the target but skips the invalidation. `__harness.openView()` does the same for a view. `__harness.reload()` fires `tabs.onUpdated` with `status: "complete"`, which always invalidates because a real load wipes the Page Bridge. `__harness.closeTab(1)` fires `tabs.onRemoved` so the "Power Tools lost its tab" banner renders; `tabs.query` then offers tab 3 ("Active Accounts"), and picking it rebinds the session and moves the watcher onto that tab. `__harness.reopenTab(1)` puts it back. `__harness.activateTab(3)` fires `tabs.onActivated` for a Dynamics tab, which the side panel follows, and `__harness.activateOtherSite()` fires it for tab 9 (`make.powerapps.com`), which the panel ignores so the binding survives a trip to another site. Each control takes the tab id as its last argument, so an event aimed at a tab the session is not bound to can be checked to do nothing.

The Extension settings section carries an "Open In Side Panel" toggle. Flipping it in the harness only writes the setting: `setPanelBehavior` is called from the background service worker, which the harness does not run, so the shim records the call but nothing changes what the toolbar icon does. The "Open in the side panel" toolbar button does work end to end here, logging `sidePanel.open` with the bound tab id.

The Security Module is backed by eight role fixtures that deliberately include business unit copies: "Basic User" exists in three business units and "Sales Manager" in two, both pointing at a root role, plus a "Field Technician" that exists only in a child business unit with no root. That is what makes the deduped role lists show "3 copies" and "2 copies" and proves a child-only role is not dropped. `security.getRolePrivileges` generates the eight table privileges across Account, Contact, Incident and Opportunity at mixed depths, with System Administrator pinned at Organization; `security.addPrivilegesRole` throws for that role, so a privilege depth run against it produces a partial failure with a real message. `security.searchSystemUsers` returns twelve users so Select all and a multi-page bulk run are reachable.

`harness-security` is the Security Tools Workspace. It reads its launch payload from seeded session storage, so it opens straight onto Role Compare; add `?securityTool=privileges` to open on the Privilege Editor instead. Removing the seed is what produces the "No security tools session" state.

The Impersonation Area's role list is backed by `security.getSystemUserRoles`: Jane Doe holds three roles directly and one through the Field Sales team, Contoso User 3 holds roles only through teams, and everyone else holds none, so the empty state renders for them. `impersonation.start` stores the roles the popup passes it, and the active view shows those instead of querying again.

The Records Area is backed by `utilities.generateFetchXml`, which on the sample form offers the current record query and one subgrid, and by `webapi.executeFetchXml`, which returns 120 sample accounts — below the 250-row cap, so the load-more path needs a larger fixture to exercise. `utilities.navigateToRecord` updates the mutable page target in the shim and logs, which is what makes the position caption and the row highlight move; in a real org the same refresh also arrives through `webNavigation.onHistoryStateUpdated`.

`harness-schema` is the Schema Tools Workspace, opening on Cross-Table Columns; add `?schemaTool=polymorphic` for the other tab. `schema.findAttributeAcrossTables` answers any name beginning `new_` with four tables: Account and Contact unmanaged, Case managed but editable, and Lead both a different type (Memo, which the tool flags) and locked by its managed solution. `schema.updateAttribute` throws for Contact, so a run across all four reads "2 of 3 applied, 1 failure" with the locked Lead never planned, and `schema.publishTables` then logs only the tables that succeeded. The polymorphic tool has no fixtures: it creates against a request shape that is not yet confirmed, so stubbing it would only prove the stub agrees with itself.

The usability pass added fixtures for the reworked screens. `security.listSystemUsers` returns forty-two users whose names repeat across a small set of first and last names, which is what makes the Bulk Users filter worth using and lets the assemble-a-set-over-several-filters behaviour be exercised. `schema.findAttributeAcrossTables` answers any `new_` name with four tables spanning two attribute types, so the type-dependent property controls show and hide as the selection changes. The Record Set Navigator view fixture names five attributes including a lookup and a link-entity attribute, so column derivation, formatted values and the link-entity exclusion are all visible. `schema.listPolymorphicLookups` returns one two-target lookup on `account`, and the create, add and remove stubs log rather than write.
