# Query Builder

Status: ready-for-agent
Decided: 2026-11-22 (grilling session)

## Problem

Writing and testing Fetch XML today means leaving the browser for FetchXML Builder in XrmToolBox: paste or build a query, run it, check that it returns the Records expected, adjust, run again. Power Tools touches Fetch XML in three places (the Data Transporter's query step, Retrieve Records, a Utilities dialog) and none of them is a place to write a query. The goal is to remove that dependency: a Workspace for writing a Query as a tree or as Fetch XML, running it, and reading the results, and then for the thing a desktop tool cannot do cheaply, running one Query against several Environments and comparing what comes back.

Two phases are committed. Phase 1 is the core loop. Phase 2 is the Comparison. Nothing after that is promised.

## Vocabulary

Terms from `CONTEXT.md`: Workspace, Module, Area, Width tier, Step explainer, Connection, Page connection, Environment connection, Gateway, Environment, Table, Column, Choice, Record, Dialect, and (added in this session) **Query**, **Query Builder**, **Query Run**, **Stored Query**, **Comparison**, **Match Key**, **System View**, **Personal View**. UI text says Table and Column in prose, messages and pickers; inside the tree and details pane, Fetch XML's own element, attribute and operator names are used as written (decision 27).

## Decisions

1. **A Workspace in its own Module.** Module **Query Builder** with one Area, `querybuilder.builder`, `fit: "workspace"`, launched as ADR 0003 describes. Workspace id `query-builder`.
2. **Fetch XML is canonical** (ADR 0004). The model mirrors the Fetch XML schema. Anything it does not recognise survives a parse and serialise untouched. Other Dialects are one-way outputs with warnings.
3. **Written from Microsoft's documentation.** No code is ported from FetchXML Builder (GPL-3.0) or from `MarkMpn.FetchXmlToWebAPI` (unlicensed). Implementers do not read either. The references are the Fetch XML reference and schema, "Query data using FetchXml", "Page results using FetchXml", and the Web API query documentation on learn.microsoft.com.
4. **Read-only.** Query Builder never writes Records, views or metadata. Its Gateway operations are all reads, in their own operations factory, so the Workspace cannot reach a write.
5. **Both Connections.** A Page connection runs as the signed-in user; an Environment connection runs as the Service Principal. Switching Connection keeps the Query, clears the results and reloads metadata.
6. **Runs only when asked.** A Run button and Ctrl+Enter. Nothing runs while editing.
7. **Three panes.** Tree on the left, XML on the right, results across the bottom; each resizable and collapsible, and the results pane can be maximised to fill the Workspace and restored. Selecting a tree row highlights its XML and moving the cursor in the XML selects its row.
8. **Two editors, one Query.** Typing in the XML pane never reformats. A tree edit regenerates the whole XML in standard formatting (two-space indent, double quotes, self-closing empty elements), keeping comments but not hand-made indentation or attribute order. While the XML does not parse, the tree stays on the last valid Query, greyed with a banner naming the error, and Run is disabled.
9. **Rows you edit in place, plus a details pane.** Each tree row is its own editor for the quick edits: a condition row is Column, operator, value inline. Beside the tree, a details pane shows every attribute of the selected row, both the ones on the row and the rarely used ones, with a short description only where the name is not enough (decision 31); the row is the shortcut and the pane is the whole picture, and they edit the same Query. The pane is resizable and collapsible, and when collapsed the whole strip is the button that reopens it. Inline controls size to their content, between a minimum and a maximum, so a value is not clipped on the row while there is room for it. Built on Fluent `Tree`, reordering by keyboard and buttons, no drag-and-drop library. This came out of a throwaway prototype, kept on the `prototype/query-builder-tree` branch under `src/query-builder-prototype/` (variant D is the one chosen): inline rows alone (variant A) hid too much behind a popover, a read-only tree with a property panel (variant B, how FetchXML Builder works) made every edit a round trip, and sections in place of a tree (variant C) were too noisy. Feasibility finding (Fluent `react-tree` 9.16.6, `useTreeItem`): inputs inside a `TreeItemLayout` keep their keystrokes, because the item's key handler acts only when the event target is the item itself, provided the editors stay out of the `actions` slot. Clicks are the problem: a click anywhere in a row, including a pick in a dropdown's popup, toggles the branch and pulls focus to the row. The fix is two handlers on the root `Tree`, cancelling click navigation and ignoring click-driven open changes unless the row itself was clicked, so only the chevron toggles.
10. **The whole schema gets an editor.** Every current Fetch XML element and attribute is modelled: aggregates and grouping, `valueof`, every link type, link-entity inside filter, fetch-level options. Common attributes sit on the row; the details pane lists all of them, in three groups (decision 30), and is generated from the schema catalogue. An element the catalogue does not know shows as a plain row editable only in the XML.
11. **Exclude a row to test without it.** Any row except `fetch` and `entity` can be Excluded, and Included again. It is a test aid: leave one small piece out, run the Query, put it back, and compare. It is not a way to keep notes in a Query; nobody ships Fetch XML with pieces commented out. An Excluded row is written into the XML as a comment holding the element, because that is the only way Fetch XML can carry it, and a comment whose content parses as one element valid at that position is read back as an Excluded row; any other comment is a comment row. A row with Excluded rows beneath it, or with a comment inside it, cannot itself be Excluded until they are Included or removed, because XML comments do not nest. `--` inside an Excluded row's attribute values is written as `-&#45;`. The control lives in a fixed gutter down the left edge of the tree, always visible and in the same horizontal position on every row whatever its depth, apart from the row's other actions, so a run of rows can be Excluded by moving straight down. When a Query has Excluded rows the tree says how many, and offers Include all and Delete excluded. The minified and string-escaped copies leave Excluded rows out; the formatted XML is always exactly what is in the editor. (This was called "switch off" until the user tried it; issues 01 to 09 use the old words.)
12. **Names.** The tree shows logical names with display names beside them, with a toggle to swap which leads.
13. **Typed value editors.** Choice (multi-select for list operators), yes/no, date, number, Record lookup (the shared `RecordLookup`, writing `value`, `uiname` and `uitype`), text, and a switch to compare against another Column (`valueof`). The operator list is filtered by the Column's type; changing Column resets an operator that no longer applies.
14. **The XML pane is a real editor.** Autocomplete knows the schema (elements valid under the current parent, attributes of the current element, enumerated values, operators) and the Connection's metadata (Table names, Column names of the enclosing Table, relationship endpoints). Validation errors are underlined in place.
15. **Validation is correctness only.** Structure, required attributes, Table and Column exist, operator fits the Column type, value count fits the operator, alias rules, aggregate rules, `top` combined with `page` or `count`. No performance tips. Problems show on the tree row and under the XML.
16. **Results are for checking.** First page on Run, then Next page and Load all (with a stop button and a warning at 50,000 Records). Record count and elapsed time. A friendly/raw toggle. Linked-Table Columns appear under their alias. Clicking a Record or a lookup value opens it in the Environment. A second view shows the raw Web API JSON. No export.
17. **Page size.** 50 unless the Query sets `count` or `top`, which are always respected. A Query with `top` or `aggregate` is a single page.
18. **Long queries.** A Query too long for a URL is sent in a `$batch` request.
19. **Starting points.** Blank (pick a Table), pasted Fetch XML, a System View or Personal View of a Table (read-only; Personal Views are new to the codebase), and, when the Workspace has a source tab, the grid or subgrid on that page. The Utilities Fetch XML dialog gets "Open in Query Builder".
20. **Remembering.** The working Query survives closing the tab (one slot; with two Workspace tabs open the last edit wins). Every Query Run is added to a history of the last 100: Fetch XML, Connection, time, Record count, never result data, with a Clear button. A Query can be kept as a Stored Query under a name, in a flat list labelled "My queries". All in the extension's local storage. One Query per browser tab.
21. **Outputs.** Fetch XML formatted, minified, and escaped as a JavaScript or C# string, and the Web API URL. Nothing else in these two phases.
22. **One converter.** The Query core is a pure shared library. The Utilities dialog's regex `fetchXmlToOData` is replaced by it.
23. **Metadata.** Loaded lazily per Table through TanStack Query, cached in memory for the session. The pickers use the first Connection's metadata.
24. **Left alone.** Retrieve Records, the Results Viewer and the Data Transporter's query step are not changed.
25. **Phase 2: several Connections.** A Query can be run over any number of Connections at once. Each Query Run has its own results, count, time and error. A Connection whose Environment lacks a Table or Column the Query uses shows that as its error and the others still run.
26. **Phase 2: Comparison.** Between two Query Runs the user picks. Records are paired by a Match Key: the primary key by default, or Columns the user chooses. Output is the counts side by side, then Records only in the first, only in the second, and in both with differing values, with the differing Columns shown side by side. Only the Query's own Columns are compared; the user can untick Columns to ignore. Lookups are compared by the referenced Record's name when the Match Key is chosen Columns and by id when it is the primary key. A Comparison loads every page of both Query Runs first, and says so plainly if either side was cut off at 50,000.

27. **The Query Builder speaks Fetch XML.** Labels in the tree and the details pane are Fetch XML's own words, not paraphrase: `AND` and `OR` for a filter's type, `alias`, `link-type`, `descending`, element names (`fetch`, `entity`, `attribute`, `order`, `filter`, `condition`, `link-entity`) and operator names (`eq`, `like`, `last-x-days`), with the plain-English meaning as secondary text in menus and as the hint in the details pane. A Choice or yes/no value shows its label and its stored value together. Nothing is abbreviated beyond what Fetch XML itself abbreviates. Table and Column names follow the names toggle. This is a deliberate exception to the glossary's rule that UI text says Table and Column: the user of this Workspace is reading and writing Fetch XML and needs the tree to read as the XML does.
28. **Every picker is searchable.** Tables, Columns, relationships, operators, link types, aliases and single Choice values are all picked through one shared control: click or tab in, type, and the list filters as you type. It matches the logical name and the display name (for an operator, the literal name and its plain-English meaning; for a Choice value, the label and the number), ranks names that start with what was typed first, highlights the match, and is driven entirely from the keyboard. A half-typed query is never written to the Query: leaving without picking restores the current value. Real Environments have hundreds of Tables and hundreds of Columns per Table, so the control caps what it renders and says how many more there are.

29. **New elements land with their kind, and Tidy regroups on demand.** Adding an element from the tree puts it after the last sibling of the same kind, or, when there is none, where that kind belongs in the standard order: under `entity` and `link-entity`, `all-attributes` and `attribute`, then `order`, then `filter`, then `link-entity`; under `filter`, `condition`, then `filter`, then `link-entity`. It is never appended blindly to the end. A **Tidy** action regroups a whole Query into that order when asked, keeping the relative order inside each kind (so sort precedence and result column order do not change), keeping each comment and switched-off row with the element it sits above, and leaving unknown elements where they are relative to each other at the end. Nothing is ever regrouped automatically: pasted or hand-written XML keeps its order until the user presses Tidy. Several `order` elements are valid Fetch XML and mean sort by the first, then the second; each order row shows its precedence number when there is more than one. There is no drag and drop: landing in the right place, Tidy, and move up and down cover it.

30. **The details pane has three groups.** Main: what a person normally sets on the element, always shown, with no heading; everything on the tree row is here. More options: documented attributes used now and then, under a heading, collapsed until asked for. Legacy and view settings: attributes the reference marks as legacy or that only saved views write, and anything in the XML the catalogue does not know, collapsed until asked for. A collapsed group says how many of its attributes are set and opens by itself when one is set or has a problem. An attribute moves to Main when the Query makes it necessary, such as `aggregate`, `groupby` and `alias` in an aggregate Query. In Main, a field that a valid Query does not require is marked "(optional)"; the other groups are optional throughout and say so once, in the heading. The first version listed every attribute in one run, and on `fetch` nothing but the order told the important ones from the rest.
31. **Few words, in Simplified Technical English.** A description is shown only when a name does not tell a developer who knows Fetch XML what the thing does; `name`, `alias`, `top` and the like have none. What remains, and every message, tooltip, banner and warning the Query Builder shows, follows ASD-STE100: one idea in a sentence, 25 words or fewer, active voice, simple present for facts and imperative for instructions, one word for one thing, no contractions, no "should".

## Architecture

**Query core**, `src/shared/lib/fetchxml/`, pure, no React, no extension APIs, tested in the node environment (so no `DOMParser`). It is imported from `@/shared/lib/fetchxml` and is deliberately not re-exported from the `@/shared/lib` barrel, and nothing in the page bundle, the background, or the Gateway operations may import it, because doing so pulls the parser into `page.js` and `background.js`:

- A parser that turns Fetch XML text into a generic ordered tree of elements, attributes (in source order), comments and text, each with its source range. Build it on `@lezer/xml`, which is already in the bundle through `@codemirror/lang-xml`, is error-tolerant, and gives positions. Parse errors are returned, not thrown.
- A serialiser with the standard formatting, a minified form, and the string-escaped forms.
- A schema catalogue: for each element, its attributes with a value kind (enumeration, boolean, number, text, Table reference, Column reference, alias reference) and its permitted children; and an operator catalogue: for each operator, which Column types it applies to and how many values it takes.
- Edit operations on the tree (set attribute, add, remove, move, switch off and on) that return a new tree.
- `validate(query, metadata)` returning diagnostics with severity, message, node and range.
- `toWebApi(query, metadata)` returning the path and a list of warnings for whatever the Web API cannot express.
- Node identity is the node's index path, so selection and expansion survive a re-parse.

**Operations**, `src/shared/lib/dataverse/query.ts`, a `queryOperations(http)` factory following the Gateway recipe (commands in `src/messaging/contract/commands.ts`, page handlers, `defineGateway`): list Tables; read one Table's Columns (type, Choice options, lookup targets), its relationships in both directions with navigation property names, entity set name, primary id and primary name; list a Table's System Views and Personal Views with their Fetch XML; run one page of a Query with annotations, returning rows, whether more exist, and the paging cookie. Reuse the readers in `codegen.ts`, `tableMetadata.ts` and `transport.ts` where they already return what is needed. Column metadata `$select` must stay on base properties with a typed cast per attribute type (see the note in project memory; a harness stub will not catch this).

**Workspace**, `src/query-builder/` and `src/entrypoints/query-builder/`, registered the way Schema Tools is (`WorkspaceId`, launch type, `WORKSPACE_PAGES`, launch storage item, `areaWorkspaceLaunch`, `WorkspaceOutlet`, a Module in the registry, a line in `dev/harness/build.mjs`). The launch payload carries the source tab or Environment and, optionally, Fetch XML to open with. State is one Zustand store: the XML text, the last valid Query, the parse error, the selection, and the Query Runs.

**Storage**: three new items in `src/shared/storage/items.ts` (working Query, history, Stored Queries), versioned as the existing items are.

## Verification

Unit tests carry the Query core: round trips (parse then serialise is stable; unknown attributes and elements, comments and switched-off rows survive), every edit operation, the catalogues against the documented schema, validation rules, and `toWebApi` including nested filters, link-entities in both directions, and the query functions for date operators. Operations are tested with `createFakeHttp`. The harness gets a `harness-query-builder` page with stubs for every new command and fetch route, enough metadata for two related Tables, a paged result, and a second Environment whose data differs for the Comparison.

A real org is needed, and the harness cannot stand in, for: paging with the cookie over both Connections, the shape of linked-Table Columns in results, `$batch`, Personal Views, the `$select` on Column metadata, and opening a Record from an Environment connection. Each phase ends with a smoke-test checklist for the user to run against a real org.

## Out of scope

Saving or editing views, layout XML, export, AI, parameters in a Query, reading a Web API URL or SQL in, Flow, C# QueryExpression, SQL, Power Fx and Liquid outputs, pushing a Query onto the open grid, folders for Stored Queries, several Queries in one browser tab, drag and drop in the tree, performance tips, a persistent metadata cache, and any change to Retrieve Records, the Results Viewer or the Data Transporter.

## Acceptance

Phase 1:

- The navigation drawer has a Query Builder Module whose Area opens the Workspace directly, in a tab from the popup and side panel and in place in the pinned window.
- Pasting a Fetch XML query with nested filters, two link-entities, a comment and an attribute the catalogue does not know shows the matching tree; changing one condition's value in the tree changes only that value in the XML's content, and the unknown attribute and the comment are still there.
- Breaking the XML greys the tree, names the error, and disables Run; fixing it restores both.
- Switching a condition off comments it out in the XML, and Run returns the wider result; switching it on restores it.
- Run over a Page connection and over an Environment connection returns the first 50 Records; Next page and Load all work past 5,000 Records; a Query with `top="10"` returns 10 and offers no paging.
- Typing `<condition attribute="` in the XML pane offers the enclosing Table's Columns; an unknown Column is underlined and flagged on its row.
- Starting from a System View and from a Personal View loads that view's Fetch XML; starting from the open page's grid loads the grid's.
- Closing and reopening the Workspace restores the working Query; the Query Run appears in history; a Stored Query can be saved, reopened and deleted.
- The Web API URL for a Query with a nested `or` filter and a many-to-one link-entity returns the same Records as the Fetch XML; the Utilities dialog shows the same URL.

Phase 2:

- One Query run over three Connections shows three counts; one Connection missing a Column shows its error while the other two show results.
- A Comparison by primary key between two Environments lists Records only in each and Records whose compared Columns differ, with the differing values side by side.
- The same Comparison with a Match Key of one chosen Column pairs Records whose GUIDs differ, and a lookup pointing at same-named Records in each Environment is not reported as different.
